## 1. DOC-001 剩下的那条建议：单条指令失败要不要返回非 2xx

**现状**：任何业务失败都返回 HTTP 200，失败信息只在 body 的 `ok` / `records[].status`。
本轮已把这条写在三份文档的顶部，并给 `/v1/status` 的 `lastCompile` 加了
`requestedUtc` + `rejectedReason`（被拒时 `requestedUtc` 会比 `finishedUtc` 新）。

**待定**：反馈里的建议 2——单条执行失败时返回 409（`batch` 内部仍汇总成 200）。

| | 好处 | 代价 |
| --- | --- | --- |
| 做 | 只看状态码的调用方立刻能发现失败 | **破坏性**：所有旧调用方一夜之间从"成功"变成"抛异常/HTTPError"；`send.py` 与 MCP 桥、你写过的所有批处理脚本都要跟着改；而且语义上开始自相矛盾（batch 200 / 单条 409） |
| 不做 | 零兼容风险 | 仍然只有"看 body"这一条路，靠文档约束 |

**我的倾向**：不做。状态码留给网络/协议层，业务结果统一看 body——这样 batch 与单条是同一套语义，
也符合 HTTP 本身的用法。真要照顾"只看状态码"的调用方，不如在客户端 SDK 里把 `ok:false` 转成异常。

**用户批注**：可以不做，但需要考虑扩大执行失败时的报错，确保 AI 解析返回时可以注意到有指令调用失败。仅 ok:false 可能会被上下文淹没。

## 2. IMPR-004 要不要改 `data` 的结构

**本轮做的**（最低成本、零破坏）：消息里加一句「`data` 为各字段修改前的旧值」，并在指令描述里写明。

**待定**的是另外两条：

- 方案 2：`data` 改成 `{"old": {...}, "new": {...}}`
- 方案 3：单数 `component.setField` 的 `data` 也从「字段名字符串」改成复数那样的旧值对象，两边统一

两者都要改 `data` 的形状。倾向：**都不做**。真要"写后的值"，调用方 `component.get` 一次就有，
没必要在返回体里塞两份；统一单复数 `data` 则纯粹是审美收益，代价是所有现有解析代码。

**用户批注**：考虑到调用方为 LLM，单次给到全部数据比规则约束更有效。所以按照方案2执行

## 3. IMPR-005 序列化写入通道要不要继续扩

现在这条兜底通道支持：**数值 / 布尔 / 字符串 / 枚举 / 颜色 / Vector2~4**。
反射优先、只对"反射原本会报错"的字段生效，所以不影响任何现有行为。

暂不支持（会明确报错并提示"写到具体分量"）：

- `MinMaxCurve`（粒子 `startSize` / `startSpeed` 的整体值）——现在只能写 `.scalar` 这类分量
- `Gradient` / `AnimationCurve`（颜色/速度曲线）
- `ObjectReference`（材质、贴图等引用）

**要不要继续做？** 收益是可完整调粒子，成本是要为每个类型写一遍 Json↔序列化的双向转换，
尤其 MinMaxCurve 还得同步 `minMaxState`（写 `scalar` 不改 minMaxState 的话 Inspector 里看着没变）。
我倾向**先按现在的分量写法用一段时间**，看实际够不够，再决定。

**用户批注**：不扩展，但需要注意这类“提议”的出现频率。如果频率过高，可能需要寻找替代方案。

## 4. `component.add` 的目标解析变严了（顺带的行为变更，提醒不是提问）

IMPR-006 统一入口时，把 `component.add` 的 Prefab 分支从 `FindInPrefab`（同名取第一个）
换成了共用的 `ResolvePrefabTarget`（内部 `FindInPrefabUnique`，**同名会报歧义**）。

- 好处：和 `setField` / `remove` 一致，不会再"静默改错节点"
- 风险：如果哪份现成的 JSON 指令里靠重名节点蒙混过关，现在会失败

我按"不静默选一个"这条既定原则改了，但如果哪天某条指令突然报歧义，记得是这个改动。
