## 症状

开着 logcat 抓取、但设备安静一段时间（或被过滤到一条都不剩）之后，
**编辑器里所有日志的调用栈都没了**——包括用户自己脚本的 `Debug.Log` / `Debug.LogError`，
与 ADB 无关的代码也一样。要等到「下一次设备有日志进来」「停止抓取」或「域重载」才恢复。

表现得很像"Unity 抽风"，因为 `Application.SetStackTraceLogType` 改的是**编辑器全局偏好**
（Windows 上是注册表），用户不知道是调试台在背后改的。

## 根因

`Tick` 把 `ReleaseStackTraceSuppression()` 只挂在了"有活"的分支里：

```csharp
if (!Lines.IsEmpty || _pending != null)
{
    BeginStackTraceSuppression();
    try { Drain(); FlushIfIdle(); }
    finally { ReleaseStackTraceSuppression(); }
}
```

注释写的是"有活才碰堆栈设置：完全静止时不写 EditorPrefs"——**少算了一件事**：
窗口到期的判断也在那个 `finally` 里。抓取过程中设备一安静，这个分支就再也不进，
`_suppressUntil` 再没人看，`_stackSuppressed` 永久停在 true。

本意是"活动期间抑制、窗口到期就还原"，实际是"活动期间抑制、静止期间无限延长"。

## 复现

1. 开着 `adb.logcat.start`，看到日志进来
2. 让游戏静默（退出到主菜单 / 停掉打日志的逻辑）超过 500 ms
3. 在编辑器里任意脚本 `Debug.Log("x")` → 控制台里这条没有调用栈

同一时刻 `/v1/status` → `adb.logcat.status` 仍然显示正常运行，看不出异常。

## 怎么修的

`Tick` 增加 else 分支：

```csharp
else
{
    ReleaseStackTraceSuppression();
}
```

`ReleaseStackTraceSuppression` 本身就有双重保险——`!_stackSuppressed` 直接返回、
`DateTime.Now < _suppressUntil` 也直接返回，所以"没活"时每帧调它只是两次比较，
不会碰 EditorPrefs，原来那条"静止时不写盘"的意图完好。
