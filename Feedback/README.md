# 反馈表

**用途**：在**其它工程**里用这套 MCP 指令系统时踩到的 bug、缺的指令、要改的行为，统统写进这里，
回到本仓库统一修。修完把文件移到 `已实现/`，编号不变。

**一条反馈 = 一个 `.md` 文件**。文件名即编号：`BUG-001-按钮点了没反应.md`。

```
Feedback/
├── README.md          ← 本文件：规则
├── _模板.md            ← 复制这个开始写
├── 索引.md             ← 由 Tools/feedback_index.py 生成，别手改
├── 待拍板/             ← status = pending：要用户拍板的，用户直接在文件里写决策
├── 未实现/             ← status = open / wontfix
│   └── BUG-001-xxx.md
└── 已实现/             ← status = done
    └── FEAT-002-xxx.md
```

## 状态怎么变

**移动文件就是改状态**，没有第三个地方要同步（`status` 字段跟着改，`updated` 跟着改）：

| 状态 | 含义 | 放哪 |
|---|---|---|
| `pending` | 要拍板，等用户决定 | `待拍板/` |
| `open` | 待处理。默认值 | `未实现/` |
| `wontfix` | 确认不做 / 复现不了 / 不适用。**也要写理由** | `未实现/` |
| `done` | 已修好、已提交 | `已实现/` |

修完一条的最小动作：`git mv` 到 `已实现/`，把 front-matter 的 `status` 改 `done`、`updated` 改当天、
在正文末尾加一段「怎么修的」。然后跑一次 `python Tools/feedback_index.py`。

## 待拍板：需要用户决定的事

**凡是"我不该替用户决定"的**（改协议、破坏兼容、加依赖、要不要继续扩能力、动别人仓库的文件），
一律写进 `待拍板/`，**不要**留在 `未实现/` 里猜，也不要自己拍。

1. AI 把选项、代价、倾向写清（`_模板.md` 里有「待拍板」小节），`status: pending`。
2. **用户在文件里直接写决策**（在问题下面加「用户批注：……」即可，格式不限，正文不用重排）。
3. AI 读完决策去实现 → 验证 → 部署 → 再把文件移到 `已实现/`，`status: done`，末尾补「执行结果」。

零散的一条一件事，用编号文件（`IMPR-007-xxx.md`）；一轮攒了好几条，用**决策批件**：
`待拍板/待拍板-YYYY-MM-DD.md`，一次列完，用户逐条批注。批件不参与编号校验，
执行完同样移到 `已实现/`（`已拍板-YYYY-MM-DD.md` 这类文件名脚本按批件识别）。

## 编号

`BUG-` / `FEAT-`（新指令、新能力）/ `IMPR-`（已有行为改进）/ `DOC-`。三位数递增，**跨状态唯一**：
一个 bug 修好后编号不换，只是换了目录。编号被脚本校验，重了直接报错。

不知道下一个可用编号？`python Tools/feedback_index.py` 会打印出来。

## 必填字段

`id` `type` `title` `status` `source` `created`。缺一个脚本就报错。
`source` 写来源工程目录名（如 `CivelRev` / `project_island` / `majotavern`），
这是判断"只在那个工程才炸，还是通用问题"的唯一线索，别省。

## 写的时候

**必须能复现**。至少给：什么工程、哪条指令 / 哪个文件、输入的 JSON、期望什么、实际什么、报错原文。
拿不到这些就写"复现不了，症状是……"，别猜。

**一个文件只写一件事。** 「ui.button 有两个问题」拆成 `BUG-003` / `BUG-004`。
混在一起修的后果是以后查不到是哪个改动解决的。

## 给 AI 的约定

1. 处理反馈前先读 `索引.md`，别一条条翻文件。
2. 改代码 → 验证（C# 改动跑 `Tools/verify_unitypackage.py --with-ui`，Python 跑一遍实际指令）→ 才允许移文件。
3. **修完必须部署到各工程**：`python Tools/deploy.py --verify`（目标编辑器开着就顺带编译校验）。
   只在仓库里改完不移文件，等于没修——`source` 那个工程里跑的还是旧代码。
   部署成功后再移反馈文件。
4. 移文件时同步 `status` / `updated`，正文补「怎么修的」小节，**不要删原文**（原始症状是以后的回归测试线索）。
5. 一次只处理一条，处理完立刻重跑 `Tools/feedback_index.py`。
6. 需要用户拍板的一律进 `待拍板/`（见上一节），**别自己决定、也别拖着不写**。
7. **「建议扩展」要记账**：想扩能力但用户没点头时，别顺手做，写成一条 IMPR 并把
   `proposal: true` 写进 front-matter。这类提议攒到 3 条就该停下来找替代方案，
   而不是继续往下堆（IMPR-005 的拍板口径，脚本会在索引里提示）。
